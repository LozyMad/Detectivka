# Доступность detektum.ru и сравнение с kodgoroda.games

Проверка: 3 октября 2026 года, повторное сравнение в 17:44–17:47 по Москве.
Пользователь находится в Курске; домашний и мобильный оператор — Билайн.
Это два способа подключения через одного оператора, поэтому дополнительно использованы независимые точки проверки.

Дополнительные проверки:

- HTTP по IP без DNS дал аналогичную разницу. Это исключает исключительно ошибку DNS или сертификата как объяснение этой серии измерений.

- Принудительный TLS 1.2 ранее не восстановил доступ к основному домену.
- Внутри VPS пользователь получил HTTPS 200 через 127.0.0.1 с правильным именем сервера. После завершения деплоя [проверка GitHub Actions](https://github.com/LozyMad/Detectivka/actions/runs/37128921311) также прошла для обоих имён.

Российские узлы Check-Host расположены в дата-центрах: Москва AS14576, Москва и Петербург AS210644. Они не заменяют измерения во всех домашних и мобильных сетях. Тайм-аут сервиса примерно три секунды означает отсутствие быстрого ответа, а не доказательство вечной недоступности. Пользователь отдельно наблюдал длительный тайм-аут в браузере.

Проверена публичная стартовая страница игрового кабинета конкурента. Покупка, авторизация и полноценный игровой сеанс не проверялись. По внешним данным нельзя установить их резервирование, SLA или внутреннюю архитектуру.

Идентификация сетей: [RIPE RDAP — Beget](https://rdap.db.ripe.net/ip/159.194.245.92), [Tilda](https://rdap.db.ripe.net/ip/176.57.66.55), [Yandex Cloud](https://rdap.db.ripe.net/ip/51.250.46.158). DNS-серверы конкурента находятся у Cloudflare, но это само по себе не означает проксирование сайта через Cloudflare. Веб-ответ главной содержит Server: ddos-guard и x-tilda-server.

## Что это означает

На момент проверки приложение обслуживает некоторые подключения, но доступ к его публичному адресу из других сетей срывается. Больше всего данные указывают на выборочную сетевую проблему: фильтрацию, маршрутизацию или правила защиты/доступа со стороны инфраструктуры. Последнее пока также не исключено.

Не установлено, кто именно отбрасывает пакеты. Для этого нужны наблюдение трафика на VPS во время неудачного клиентского подключения и проверка Beget. Нельзя утверждать, что detektum.ru внесён в реестр блокировок, что виноват только Билайн или что заблокирован весь Beget.

Различие с конкурентом конкретное: посетители его главной подключаются к инфраструктуре Tilda/DDoS-Guard, а посетители игрового кабинета — к адресу в сети Yandex Cloud. Наш сайт принимает подключения непосредственно на одном адресе Beget. Эти адреса и сетевые пути имеют разную доступность в проведённых тестах. Отдельно доказать, что успех главной обеспечен именно функцией анти-DDoS, эти измерения не позволяют.

Проблемы прежнего VPS Timeweb могли иметь другую причину: на скриншоте были сообщения Out of memory и сбои системных служб. Их нельзя автоматически объяснить тем же сетевым ограничением. Перенос устраняет неисправность старого сервера, но не обеспечивает доступность любого нового сетевого пути.

## Практический план для проекта

1. **Проверить текущий сетевой путь с Beget.** Передать результаты и попросить проверить сетевые ACL, анти-DDoS и маршруты. Запросить возможность предварительного теста адреса из другой подсети. Менять адрес полезно только после сравнения из проблемных сетей; соседний IP может иметь ту же проблему.
2. **Испытать вход через независимую сеть.** Разместить обратный прокси перед текущим приложением. Посетитель подключается к этому прокси, а прокси — к Beget. Проверить оба участка пути. Это позволяет сохранить работающий сервер и базу, изменив публичную точку входа. Прокси не устраняет падение приложения или самого VPS.
3. **Переключать основной домен после испытания.** Проверить домашний и мобильный Билайн, другой оператор и независимые российские точки. Проверить авторизацию, создание и подключение к комнате, передачу игровых событий. Один ответ главной страницы 200 недостаточен. Для испытания можно использовать отдельное имя и затем дополнительно проверить основной домен с принудительным IP.
4. **Добавить независимые резервные копии и резервный сервер.** Сохранять согласованные копии основной SQLite, баз сценариев и загруженных файлов вне Beget; проверить восстановление. Первоначально — один активный сервер и ручное переключение на восстановленный резерв с явно определённой допустимой потерей данных.
5. **Настроить проверки со стороны пользователей.** Контролировать основной домен, www, вход и игровой API из разных российских сетей и с зарубежной точки. Проверка GitHub после деплоя полезна, но не выявляет все ограничения российских операторов.

В проекте SQLite и подписки на игровые события в памяти одного процесса: backend/config/database.js, backend/config/scenarioDatabase.js, backend/sse/roomEvents.js. Поэтому два независимых сервера с отдельными копиями базы нельзя просто одновременно включить под балансировщиком: пользователи и события начнут расходиться. Полноценный активный резерв требует отдельной работы с базами и передачей событий.

Для прокси обязательны: HTTPS на обоих участках; отсутствие кеширования авторизации и игрового API; поддержка длительных SSE-соединений без буферизации; сохранение нужных заголовков; ограничения загрузки файлов не меньше текущих. CDN только для картинок не решит недоступность игры.

DDoS-Guard — кандидат для испытания, потому что через его инфраструктуру сейчас доступна главная конкурента. Это платная услуга; на [странице сервиса](https://ddos-guard.ru/web-protection) указан бесплатный тест Basic на три дня. До покупки нужно подтвердить подходящий тариф, HTTPS до исходного сервера и поддержку SSE. Другой VPS с Nginx в независимой сети также можно испытать как прокси, но обслуживать его придётся самостоятельно. Наличие DDoS-защиты не гарантирует доступ через любые ограничения оператора.

При режиме мобильного интернета «только разрешённые сервисы» гарантии обычным выбором хостинга нет. Для игры полезен отдельный план продолжения сеанса при потере сети: восстановление подключения и, если продукт этого требует, заранее доступные материалы. Такой режим ещё не реализован.

## Дополнение: ответ поддержки Beget от пользователя

Поддержка сообщила, что воспроизвела проблему из сети Интерра, а из своей рабочей сети соединение устанавливается. Компания считает поведение характерным для фильтрации ТСПУ по адресам или подсетям, но прямо указывает, что точный критерий установить не может. Это усиливает гипотезу о сетевой фильтрации, не превращая её в доказанную конкретную причину.

В приложенном фрагменте tcpdump видны повторные TCP SYN к 159.194.245.92:80 и нет ответных пакетов. Несмотря на упоминание SSH-баннера в тексте поддержки, сам фрагмент не содержит SSH-баннера или полезных данных: length 0, порт 80. Он показывает отсутствие завершённого TCP-соединения со стороны источника. Только по этому фрагменту нельзя определить, теряется запрос по пути к VPS или ответ в обратном направлении.

Предложенный следующий шаг — смена внешнего IP того же VPS через настройки сети Beget. По инструкции поддержки старый адрес 159.194.245.92 нужно открепить, а не удалять самостоятельно, и сообщить им для резервирования и дальнейшей проверки.

Порядок проверки:

1. Получить и назначить новый адрес тому же VPS; по возможности предварительно запросить адрес из другой подсети. Сохранить доступ к консоли панели Beget на время смены.
2. До изменения DNS проверить HTTPS с именем detektum.ru и принудительным новым IP, затем www аналогичным способом. Проверку выполнить из проблемной сети, а также независимых российских точек.
3. Если новый адрес доступен, заменить IP в обеих A-записях REG.RU: @ и www. Сертификат относится к доменам, поэтому сама смена IP не требует нового сертификата или установки проекта заново.
4. Проверить сайт после обновления DNS с домашнего и мобильного подключения, включая игровой сеанс. Сохранить результаты успешных и неуспешных тестов.
5. Передать поддержке старый адрес для согласованной обработки. Если новый адрес тоже недоступен, продолжить проверку другого сетевого входа; не повторять переносы вслепую.

Замена IP пока не выполнена; ответ поддержки добавлен как предоставленная пользователем информация.

- Из трёх российских точек HTTPS detektum.ru уже получил 200 на новом адресе, примерно за 3,1–3,3 секунды. Это может включать задержку выбора адреса; причина задержки отдельно не установлена. [Отчёт](https://check-host.net/check-report/4ecc9eaekaf3).
- Новый IP:443 доступен из всех пяти точек, как и HTTP по IP. [TCP](https://check-host.net/check-report/4ecc9ec8k8a5), [HTTP](https://check-host.net/check-report/4ecc9ed2k7a3).

Повторная смена IP пока не обоснована. В панели должны остаться A @ -> 159.194.252.192 и A www -> 159.194.252.192 без старых A-адресов. Если пользователь уже сохранил такое состояние, нужно дождаться публикации и истечения кешей; если нет, сначала исправить записи. REG.RU указывает для стандартной услуги публикацию изменений зоны не менее часа: https://help.reg.ru/support/dns-servery-i-nastroyka-zony/dopolnitelnyye-vozmozhnosti/premium-dns . Это время публикации у DNS-провайдера, отдельно от последующего кеширования у резолверов. Доступ непосредственно из проблемного подключения пользователя с выключенным VPN в этой серии не подтверждён.

## Пользовательский тест без VPN: новый адрес доступен

После предыдущих проверок пользователь выполнил в PowerShell с выключенным VPN команду curl.exe с --noproxy, IPv4 и --resolve detektum.ru:443:159.194.252.192. Получен HTTP/1.1 200 OK, Nginx/Express, без отключения проверки сертификата. Дата серверного ответа: 03.10.2026 16:16:10 UTC (19:16:10 МСК). Это подтверждает доступность HTTPS нового адреса из проблемного подключения пользователя и исключает необходимость повторной смены IP на основании текущего браузерного тайм-аута.

Следующая проверка: Google и Cloudflare DNS-over-HTTPS уже возвращают только новый адрес для основного имени. Для www оба ещё возвращают старый адрес. Прямой ответ одной из точек ns1.reg.ru по-прежнему содержит оба адреса для основного имени и старый для www. Полная сходимость ответов не подтверждена. Рекомендуются проверка сохранённых записей @/www, обновление локального DNS-кеша и повторное открытие основного домена. Проверка curl не доказывает доступность сайта во всех сетях или одинаковое поведение всех браузеров.
